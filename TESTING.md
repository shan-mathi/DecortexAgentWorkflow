# TESTING.md

## What We Built

- **58 unit tests** (`pnpm test`, <600ms) covering: DAG validation + topological sort (including property tests with 30 random DAGs), template resolution, expression sandbox (allow/deny), Branch/Transform/LLM node handlers, and full Backend API route validation against a mock engine.
- **Integration test on deployed infra** — the seed script + manual execution trigger exercises the complete path: API Gateway → Lambda → internal ALB → Fargate → Postgres → Bedrock → trace persistence. Verified via `GET /executions/:id` asserting per-node status, duration, and token usage.
- **Mock LLM as a first-class execution mode** — `LLM_PROVIDER=fake` (default for local dev and unit tests) uses pattern-matched responses: "HIGH"/"MED"/"LOW" for classification prompts, generic text for draft prompts. Same handler code path, zero cost, deterministic.

## What We Would Build Next

## C1: How We Source Test Data

**Test corpus for ops-ticket routing:**

We hand-craft tickets covering the long tail — not generated by LLMs (which collapse toward the happy path). Categories:

| Category | Example | Why it matters |
|----------|---------|----------------|
| Urgent outage | "503 across us-east-1, customers losing data" | Must route HIGH, draft acknowledges severity |
| Ambiguous | "things are slow today" | Tests that the system doesn't crash on uncertain input |
| Half-sentence rage | "down. cant login. fix asap." | Template resolution handles short/malformed text |
| Multilingual | "Service est tombé / Service is down" | LLM and template don't break on non-ASCII |
| Malformed JSON in body | `{"event": "order" and more text` | Node input is arbitrary; executor must not parse it |
| Feature request (not a bug) | "Can we get dark mode?" | Should route LOW, not trigger urgent path |
| Compliance deadline | "GDPR deletion stuck, legal pinging us" | Urgency depends on context, not keywords |

**Diversity assurance:** we assert on *structure* (`urgency ∈ {LOW,MED,HIGH}`, `draft.text.length > 0`, branch resolved to a valid target) — never on exact LLM wording. This means the same corpus works with FakeLLM (deterministic, gating) and real Bedrock (non-deterministic, non-gating).

## C2: Integration & External System Strategy

### LLM calls

| Mode | When | Cost | Determinism |
|------|------|------|-------------|
| **Mock** (`LLM_PROVIDER=fake`) | Unit tests, local dev, load tests | $0 | Fully deterministic |
| **Live Bedrock** (`LLM_PROVIDER=bedrock`) | Deployed infra, nightly eval | ~$0.001/call | Non-deterministic |

The mock lives inside the same `LLMHandler.execute()` code path — not a separate class or vi.mock. This means the template resolution, config merging, and error handling are exercised identically in both modes. The only difference is whether the prompt goes to Bedrock or to pattern-matching.

### HTTP nodes calling third-party APIs

- **Unit tests:** Fastify's `inject()` against a mock engine — no real network.
- **Integration tests:** the HTTP handler uses `fetch()` against real URLs. For tests, we'd point at a local mock server (same pattern as `tst/api.test.ts` which spins up a mock engine).
- **Production:** HTTP nodes have configurable `timeoutMs` and the executor retries on failure. If the third-party is down, the node FAILS and the trace records the error — observable, debuggable.

### Which tests run when

| Trigger | What runs | Why |
|---------|-----------|-----|
| **Every commit** | `pnpm test` (58 unit tests) + `pnpm typecheck` | Fast (<1s), deterministic, catches regressions in executor logic, template resolution, sandbox, and API validation. No I/O, no cost. |
| **Every deploy** | Seed script + manual execution on deployed infra | Verifies the full path works end-to-end with real Postgres + real Bedrock. Catches infra issues (SG rules, IAM, image version) that unit tests can't. |
| **Nightly (planned)** | Eval corpus against real Bedrock | Measures agent quality drift. Non-gating — a "LOW" classification on an urgent ticket doesn't block deploys, it creates a ticket for prompt tuning. |
| **Before release (planned)** | Load test at 50 concurrent executions | Verifies SLOs under stress. Expensive (Fargate scale-out + Bedrock calls), so not run on every commit. |

### Software correctness vs. agent quality

| Concern | Test strategy | Gating? |
|---------|---------------|---------|
| **Software correctness** — DAG runs in right order, branch routes correctly, retries work, traces persist | Unit tests + typecheck + deployed trace inspection | **Yes** — blocks every commit and deploy |
| **Agent quality** — LLM classifies correctly, drafts are helpful | Eval corpus with structural assertions (real Bedrock, nightly) | **No** — creates improvement tickets, doesn't block |

We never gate on LLM output content. A workflow that routes to the wrong branch due to a code bug is a *software correctness* failure (caught by unit tests). A workflow that routes correctly but the LLM classifies "503 outage" as LOW is an *agent quality* failure (caught by eval, fixed by prompt engineering).

## C3: Load Testing

### What happens at scale

| Load | Bottleneck | Mitigation |
|------|-----------|------------|
| **10x** (10 concurrent) | None — single Fargate task handles it | — |
| **100x** (100 concurrent) | Bedrock TPS rate limits (Nova Micro: ~50 TPS default) | Request quota increase; queue executions |
| **1000x** (1000 concurrent) | Postgres connection pool (20 max) + Fargate scale-out lag (~60s) | RDS Proxy (connection pooling), pre-warm Fargate `desiredCount`, async execution queue (SQS) |

### Simulating load without LLM cost

```sh
# Set LLM_PROVIDER=fake on the Fargate task (via CDK env var)
# Then run concurrent executions:
for i in $(seq 1 50); do
  curl -sS -X POST "$API_URL/api/executions" \
    -H 'content-type: application/json' \
    -d '{"workflowId":"<id>","input":{"subject":"load-'$i'","description":"test"}}' &
done
wait
```

With `LLM_PROVIDER=fake`, the LLM handler returns in <1ms (pattern match, no network). This isolates executor performance: DAG resolution, parallel Promise.all, DB writes, and Fargate concurrency — all without spending a cent on Bedrock.

### SLOs we would set

| Metric | Target | How measured |
|--------|--------|--------------|
| Execution P99 latency (4-node workflow) | <5 seconds | `ended_at - started_at` from `runs` table |
| API health response | <200ms | API Gateway latency metrics |
| Node execution idempotency | 0 duplicate trace rows | `SELECT count(*) - count(DISTINCT (run_id, node_id))` |
| Fargate task health | 100% healthy during load | ECS target group health check |
| Error rate | <1% of executions FAILED due to infra (not node logic) | `status=FAILED` where error contains "timeout" or "connection" |

The load test tells us if we're meeting SLOs by querying the `runs` and `node_executions` tables after the burst completes — same observability the production system uses.

## Priority Order Rationale

1. **C2 (integrations) first** — because the system has 4 services talking over HTTP. If the proxy, routing, or security groups are wrong, nothing works. The mock LLM strategy is what makes the unit test suite fast and free.
2. **C1 (data) second** — because edge-case inputs expose executor bugs (template resolution on empty strings, branch expressions on unexpected values). The corpus design determines whether tests catch real failures or just validate the happy path.
3. **C3 (load) third** — because at current scale (<10 concurrent executions), correctness matters more than throughput. But the infrastructure for scaling (Fargate auto-scaling, connection pooling, idempotent writes) is already in place.

## One Bug We Catch

**Ancestor output propagation in diamond DAGs.** `allAncestorOutputs()` walks edges backwards to collect all upstream results. Without it, `{{classify-ticket.text}}` fails with "Unknown node" when the branch is between classify and the draft node. Our `dag.test.ts` property test with 30 random DAGs ensures topo-level ordering is always correct; the `template.test.ts` verifies resolution against upstream maps.

## One Bug We Miss

**LLM classifies an urgent outage as LOW.** Every software assertion passes — status=SUCCEEDED, branch resolved, draft is non-empty. The customer gets a "we'll respond in 2 business days" reply for a P0 incident. Detecting this requires human-labelled eval sets or production escalation-rate telemetry — future investments beyond automated testing.
